# RAG：让回答使用外部资料

**一句话：** RAG（Retrieval-Augmented Generation，检索增强生成）先寻找相关资料，再把检索结果作为上下文提供给生成模型。

## 为什么需要 RAG？

例如，用户问：“最新的公开 API 文档中，错误码是什么意思？”

模型的训练数据不一定包含最新文档。RAG 让系统先查资料，再基于查到的内容回答。

## 工作流程

~~~text
用户问题
 ↓
查询处理
 ↓
检索公开或已授权文档
 ↓
筛选相关片段
 ↓
模型根据片段生成回答
 ↓
展示回答及资料来源
 ↓
核对是否真正受到来源支持
~~~

检索既可以用关键词，也可以用向量相似度或混合检索，不等于必须购买向量数据库。

## 一个简化案例

知识库包含两段虚构资料：

~~~text
文档 A：任务创建接口缺少 title 时返回 400。
文档 B：访问任务接口需要完成身份认证。
~~~

用户问：“为什么创建任务失败？”

系统找到 A、B 后，模型可以回答“可能是参数缺失或未认证，请提供实际状态码”。它仍然不能直接断言根因。

## RAG 的限制

| 失败类型 | 表现 | 处理 |
| --- | --- | --- |
| 未检索到 | 相关文档根本没进入上下文 | 检查索引与召回 |
| 找错资料 | 找到过时接口文档 | 增加版本和权限过滤 |
| 资料冲突 | 新旧规定不一致 | 显示来源并提示人工核对 |
| 引用失真 | 回答包含来源没有支持的结论 | 做引用与事实核验 |
| 权限穿透 | 检索到了无权查看的资料 | 在检索阶段执行访问控制 |

**重要：** RAG 能提高信息相关性，但不保证没有幻觉。

## 什么时候不用 RAG？

简单计算、固定规则校验或无需外部知识的任务，不需要额外增加检索链路。

**完成标准：** 能区分检索错误与生成错误。
