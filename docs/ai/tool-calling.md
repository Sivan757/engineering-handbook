# Tool Calling：从回答到执行

**一句话：** Tool Calling（工具调用）让模型提出调用外部功能的请求；真正执行操作的是宿主应用或工具运行环境。

## 一个任务查询例子

用户问：“查一下任务 T-1001 的状态。”

~~~text
用户问题
 ↓
模型判断需要查询数据
 ↓
模型提出工具调用 getTask({"id":"T-1001"})
 ↓
宿主应用检查权限、校验参数
 ↓
后端真实执行查询
 ↓
将查询结果交还模型
 ↓
模型向用户解释结果
~~~

模型提出调用并不等于工具执行成功，更不等于模型有权跳过授权。

## Tool 与普通文本的区别

| 普通回答 | 工具调用 |
| --- | --- |
| “这个任务可能已完成” | 调用查询 API 读取真实状态 |
| 可能基于已知模式推断 | 可以获得运行时数据 |
| 不直接修改系统 | 某些工具可能触发实际写操作 |

因此，工具可能增加模型能力，也引入更高的操作风险。

## 工具定义至少需要

- 清楚的工具名称与用途。
- 明确的输入字段和类型。
- 有意义的错误响应。
- 按用户权限执行的鉴权逻辑。
- 对写操作的审批或确认机制。

### 一个工具定义示意

~~~json
{
  "name": "getTask",
  "description": "查询公开演示任务状态",
  "parameters": {
    "type": "object",
    "properties": {
      "id": { "type": "string" }
    },
    "required": ["id"]
  }
}
~~~

这只是概念示例。不同模型服务的完整工具声明格式并不相同。

## 常见错误

- 将外部工具结果中的文字当成可信指令。
- 只凭模型输入决定用户权限。
- 写操作没有幂等设计或人工审批。
- 工具失败时，模型仍声称操作成功。

## 练习

设计一个 `getTask`（只读）和一个 `deleteTask`（写入）工具，并说明后者需要哪些额外保护。

**完成标准：** 能指出权限判断必须由应用执行，不能依赖模型自己承诺。
