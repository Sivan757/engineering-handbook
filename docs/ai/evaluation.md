# AI 输出如何评估？

**完成后你可以：** 为一个 AI 任务设计小规模评估集，记录失败原因，并比较提示词改进前后的结果。

## 为什么不能只凭“感觉不错”？

模型回答可能有说服力，但遗漏关键条件。不同输入或不同模型版本也可能给出不同结果。

评估（Evaluation，简称 Eval）是根据预先制定的标准检查输出是否符合目标。

## 第一步：定义任务和判定标准

示例任务：把用户反馈分成三类：

- `performance`：性能问题。
- `usability`：可用性问题。
- `data`：数据相关问题。

**验收：** 类别必须来自上述集合，并且必须与原反馈含义相符。

## 第二步：准备一个小测试集

| 输入 | 期望分类 | 检查点 |
| --- | --- | --- |
| 页面加载特别慢 | performance | 性能含义 |
| 找不到保存按钮 | usability | 交互可发现性 |
| 导出表格日期有误 | data | 数据正确性 |
| 页面慢且按钮难找 | 待人工复核 | 多问题同时出现 |
| （空字符串） | 输入无效 | 不得编造反馈 |

上表是教学示例，不是完整业务评测集。

## 第三步：记录每个结果

可以用以下结构：

~~~json
{
  "caseId": "case-01",
  "expected": "performance",
  "actual": "performance",
  "passed": true,
  "notes": "符合分类定义"
}
~~~

真正的评估必须运行模型或工作流并记录输出。以上只是演示记录格式。

## 第四步：分析失败，而不是只看总分

至少区分：

- **输入问题：** 原问题含糊或资料不足。
- **提示词问题：** 类别定义或约束不清。
- **检索问题：** 上下文缺失或来源错误。
- **工具问题：** 执行失败、超时或权限不足。
- **模型问题：** 即使输入清楚，输出仍然不符合预期。

可统计通过数 ÷ 总用例数，但仅适用于有明确通过条件的用例。对开放式任务还需要人工或经过验证的评估流程。

## 第五步：比较迭代效果

固定测试集和模型条件，对比改写前后的分类正确性、格式错误、延迟和成本。避免只挑选改进成功的例子。

## 练习

为“将反馈归类”设计至少八条虚构样本，包含正常、多义、空输入和越界情况。测试两版提示词，记录实际输出与失败原因。

**完成标准：** 能展示可追溯的测试数据，而不只是主观评价。
