# 如何写出可执行的提示词？

**一句话：** 提示词（Prompt）是交给模型的任务说明。清晰的目标和可验证的要求，比复杂的“万能咒语”更重要。

## 什么时候需要结构化提示词？

当任务有多个约束、需要格式化输出或必须与既有系统一致时，建议将要求写成清晰的几个部分。

简单问题可以直接提问，不必每次套模板。

## 六个要素

| 要素 | 需要回答的问题 | 示例 |
| --- | --- | --- |
| 目标 | 要解决什么问题？ | 为任务列表设计筛选条件 |
| 背景 | 任务处于什么场景？ | Web 应用，已有列表和状态字段 |
| 输入 | 有什么已知事实？ | 提供脱敏的字段清单 |
| 约束 | 哪些事情不能改变？ | 保持旧接口兼容 |
| 输出 | 需要呈现什么？ | 参数表、响应 JSON、测试用例 |
| 验收 | 如何判断可用？ | 覆盖正常和异常分支 |

## 对比两个提示词

**模糊：**

~~~text
帮我做一个任务管理系统。
~~~

**可执行：**

~~~text
目标：为内部练习项目设计“任务列表筛选”功能。
背景：目前只支持按创建时间排序。
输入：任务包含 id、title、status、createdAt。
约束：不修改原有字段；不引入未经说明的新权限。
输出：用户故事、API 参数建议、示例响应、三条验收用例。
验收：覆盖正常筛选、无匹配结果、非法 status 三种情况。
不知道的业务规则请列为“待确认”，不要自行决定。
~~~

第二个提示词没有保证正确，但会让输出更容易评审。

## 按工作类型调整

**产品：** 强调用户、业务目标、场景、边界和验收。

**开发：** 强调现有代码、技术栈、兼容性、测试和限制。

**测试：** 强调输入、预期结果、边界值和异常路径。

## 多轮交互如何进行？

1. 先让模型复述目标与缺失信息。
2. 核对并补充关键限制。
3. 要求先给方案，再产出具体内容。
4. 对照验收标准逐项核实。
5. 将最终要求保存为可复用模板。

## 常见误区

- “你是世界顶级专家”不能代替业务背景。
- 不需要为简单问题编写冗长提示词。
- 模型自己声称“我检查过了”，不等于真正执行了检查。
- 不要把密钥、客户信息或未授权代码直接贴给外部服务。

## 练习

将“帮我修复接口”改写为明确的问题描述，包括现象、复现步骤、预期结果、边界和核对方式。

**完成标准：** 不熟悉项目的同事也能说清需要解决的问题，以及什么情况下算完成。
