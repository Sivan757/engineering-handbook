# AI 辅助编程工作流

**适用情形：** 使用 AI 辅助理解项目、修复问题、增加功能、生成测试或编写文档。

**原则：** AI 能帮助开发，工程师仍要对需求、代码质量、验证和提交负责。

## 第一步：准备任务

写明：

- **目标：** 需要新增或修复什么？
- **范围：** 允许修改哪些模块？
- **限制：** 哪些接口不能破坏兼容？
- **验收：** 哪些测试必须通过？

不要先让 AI 无限制修改整个仓库。

## 第二步：先读代码再提出方案

~~~text
请先阅读当前任务相关的 Controller、Service 和测试。
任务：为任务列表增加可选的 status 筛选参数。
约束：保持现有接口兼容，不修改无关模块。
先列出受影响文件、依赖、风险和验证计划。
不要在完成分析前直接修改代码。
~~~

**预期结果：** 一个供人审查的修改计划，不是直接可上线的变更。

## 第三步：小范围实施

审批方案后，要求 AI 逐项修改，保留每一次文件差异。

观察是否修改了配置、鉴权或与任务无关的逻辑。

## 第四步：真实验证

1. 阅读所有代码差异。
2. 执行编译、单元测试及受影响的集成测试。
3. 检查正常、边界和错误路径。
4. 检查依赖变更、鉴权和敏感信息。
5. 在 PR 中写明已执行的命令及结果。

不能只因为 AI 说“已通过”就宣称测试完成。

## 第五步：交付审查

PR 必须回答：

| 问题 | 需要证据 |
| --- | --- |
| 修改了什么？ | 文件差异和行为说明 |
| 为什么这么改？ | 需求与技术约束 |
| 是否兼容？ | 相关测试和接口行为 |
| 是否验证？ | 真实命令、输出摘要和环境 |
| 有哪些风险？ | 未验证项、回滚方法 |

## 常见失败

- **AI 引用了不存在的 API：** 返回官方文档或项目当前代码核对。
- **AI 改动过大：** 拆成更小的任务与 PR。
- **测试只覆盖成功路径：** 明确要求异常和权限用例。
- **持续自动尝试失败：** 暂停迭代，分析实际日志和根因。

## 练习

在本地练习仓库选一个小需求，让 AI 先给方案再产生变更。执行测试后，写一段包含已验证和未验证内容的 PR 描述。

**完成标准：** 能解释每一处主要修改，并展示实际验证证据。
