# 综合实践：把需求变成可靠成果

**最终任务：** 使用 AI 协助完成一项小型产品或研发工作，并提交能独立核查的结果。

选择下面任意一种角色任务。全部材料必须是虚构或明确允许公开的资料。

## 任务 A：产品经理

背景：用户说“任务管理系统里，我经常找不到今天的任务”。

交付：

1. 事实与假设分离的问题陈述。
2. 两种改进方案及权衡。
3. 一个最小可行方案及非目标。
4. 至少四条可测试的验收标准。

**不要编造：** 用户访谈、使用数据或管理层批准。

## 任务 B：开发工程师

背景：练习项目已有 `GET /tasks` 接口，需要可选 `status` 参数。

交付：

1. 明确输入、输出和兼容性限制的任务说明。
2. 受影响代码或示例伪代码。
3. 正常、非法、空结果三类测试。
4. 代码审核与实际执行记录。

**不要编造：** 未运行的测试结果、未提供的项目文件。

## 任务 C：测试工程师

背景：练习项目新增“创建任务”操作。

交付：

1. 覆盖必填字段、边界长度和认证状态的测试用例。
2. 预期结果与实际结果记录表。
3. 发现的问题与复现方式。
4. AI 输出的事实核对记录。

**不要编造：** 未实际获取的响应。

## 所有角色统一走五步

1. **定义目标：** 说明用户、问题、成功标准。
2. **选择方式：** 单次模型调用、固定 Workflow 或人工操作，必要时使用 Agent。
3. **写清输入：** 只提供获准使用的数据、约束和输出格式。
4. **核对结果：** 检查关键事实、边界条件和真实执行记录。
5. **交付复盘：** 区分已验证、待确认、未完成事项。

## 最终自检

| 维度 | 通过条件 |
| --- | --- |
| 理解 | 能解释为什么选择这一种 AI 使用方式 |
| 清晰 | 提示词有明确目标、背景、约束与输出 |
| 正确 | 关键事实可追溯或经过测试 |
| 安全 | 没有越权操作或泄露非公开资料 |
| 可复用 | 同事能根据说明重复主要步骤 |

## 完成标准

不是生成一份看起来完整的文档，而是能向另一位同事解释：**任务是什么、AI 做了什么、哪些已验证、哪里仍有不确定性。**

完成后按 [写作规范](/team/writing-guide) 将常见问题补充到知识库。
