# Token 与上下文窗口

**一句话：** Token 是模型处理文本的基本片段；上下文窗口是单次推理能够处理的信息预算。

## Token 不是“字数”

“HTTP 请求失败”不会必然等于相同数量的 Token。不同模型使用不同的分词方式，中文、代码与标点的 Token 数也不同。

因此，不能简单用汉字数量准确计算模型成本。

## 上下文是什么？

当你请求“继续修改刚才的代码”，模型需要看到有关代码和此前的要求，这些就是当前上下文的一部分。

~~~text
系统/开发者约束
+ 用户问题
+ 历史消息的相关部分
+ 检索到的文档
+ 工具返回的内容
+ 模型生成的输出
= 一次任务要管理的上下文
~~~

上下文窗口不是永久记忆。历史对话过长、内容被裁剪或压缩时，模型可能失去早期细节。

## 为什么会影响开发？

场景：你将整个后端仓库一次性贴给模型。

潜在问题：

- 无关文件占用上下文预算。
- 重要约束被淹没。
- 更长输入通常意味着更多成本和延迟。
- 模型可能误用旧版本代码。

更好的做法：先让模型定位相关模块，再逐步提供接口、关键实现和测试。

## 三种常见改进

1. **缩小范围：** 只提供当前任务相关文件。
2. **提取事实：** 将关键约束和接口契约写成简短列表。
3. **分段验证：** 每完成一个步骤就检查输出，再继续。

## 练习

为“修复登录失败”列出必须提供的五类上下文，例如复现步骤、错误状态码、当前代码位置、预期行为和已尝试操作。不要提交真实 token 或密码。

**完成标准：** 能解释什么内容必须保留、什么内容可以省略。
